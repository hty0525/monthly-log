# 효율성과 간결함 규칙

## 핵심 원칙

### 1. 중복 최소화
- **새 파일을 만들기 전에 기존 파일로 같은 목적을 달성할 수 있는지 확인**
- 중복 파일을 발견하면 즉시 제거
- 비슷한 설정을 단일 진실 공급원(Single Source of Truth)으로 통합
- 예시: `.env.mcp`와 `mcp_config.json` 둘 다 만들지 말고 하나로 처리

### 2. 모든 파일에 의문 제기
파일을 만들거나 제안할 때 항상 질문하기:
- 이 파일이 실제로 사용되는가?
- 기존 파일로 처리할 수 있는가?
- 유지보수 부담을 만드는가?
- 더 단순한 대안이 있는가?

### 3. 완전함보다 단순함 우선
- "혹시 몰라서" 파일을 만들지 않는다 (팀 협업에 명시적으로 필요한 `.example` 템플릿 제외)
- 루트 레벨 `.gitignore`로 충분하면 중첩된 `.gitignore` 파일을 피한다
- 필요한 최소한의 설정 파일만 사용한다

### 4. 복잡성에 도전
해결책을 구현하기 전에 제안하기:
1. 가장 단순한 접근법
2. 더 복잡한 대안의 장단점
3. 실제 필요에 따라 사용자가 결정하도록

### 5. 적극적으로 정리
- 구현 중에 사용하지 않는 파일을 식별하고 제거
- 중복을 발견하면 정리 제안
- 명확한 목적이 없는 "백업"이나 "예시" 파일을 남기지 않는다

## 구체적 가이드라인

### 설정 파일
- ✅ 도구/서비스당 하나의 설정 파일
- ❌ 같은 데이터를 가진 `.env`와 설정 파일 둘 다 만들지 않기
- ✅ 가장 직관적인 접근법을 먼저 사용
- ❌ 가상의 팀 협업 시나리오를 위해 과도하게 엔지니어링하지 않기

### 보안
- ✅ `.gitignore`로 민감한 데이터 보호
- ✅ 최소한의 `.gitignore` 파일 사용 (루트 레벨 선호)
- ❌ 같은 파일을 위한 여러 보호 계층 만들지 않기

### 문서화
- ✅ 필요하고 명백하지 않은 것만 문서화
- ❌ 단순한 설정을 위한 광범위한 문서 만들지 않기
- ✅ 가능하면 별도 문서 파일보다 인라인 주석 선호

## 의사결정 프레임워크

해결책을 제안할 때 항상:
1. **가장 단순한 접근법으로 시작** - 문제를 해결하는
2. **대안은 명확한 이점이 있을 때만 언급**
3. **사용자에게 질문** - 가장 "완전한" 해결책을 구현하기보다는 어떤 접근법을 선호하는지
4. **유지보수성 우선** - 기능 완전성보다

## 피해야 할 위험 신호

- "템플릿"이나 "예시" 파일을 명시적 필요 없이 만들기
- 같은 목적을 위한 여러 설정 파일
- 루트 레벨로 충분한데 중첩된 `.gitignore` 파일
- "혹시 몰라서" 백업 파일
- 단순한 설정을 과도하게 문서화

## 이 규칙을 깨야 할 때

- 사용자가 명시적으로 포괄적인 설정을 요청
- 팀 협업이 표준화된 템플릿을 요구
- 복잡한 프로젝트가 진정으로 관심사 분리를 필요로 함
- 보안 요구사항이 심층 방어를 요구

## 요약

**항상 질문하기: "이것을 안정적으로 작동시키는 데 필요한 최소한은 무엇인가?"**

효율성은 더 많이 하는 것이 아니라 더 적게 하는 것에서 나온다. 모든 파일, 모든 설정, 모든 코드 라인은 그 존재를 정당화해야 한다.
